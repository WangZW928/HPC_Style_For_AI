# HPC_Style_For_AI

本技能帮助设计在数值、资源与工程约束下有效完成计算的程序。原则先于实现机制；不从某个成熟库的类型层次、命名或平台 API 推导所有项目都应采用的结构。

## 加载与适用范围

先读[通用原则](<references/rules.md>)，按当前问题选择 G01–G12 中相关项。原则不依赖某个案例库；按需阅读的实现说明和源码论据不应成为执行技能的前置依赖。

任务涉及提前绑定、代码生成或 C++ 模板时，再读[绑定策略说明](<references/binding-strategies.md>)。不要将模板、owner/view、线程模型或某一种布局预设为每个工程的起点。

遵循目标工程现有约定。小任务只做必要推理与改动，不为满足原则而制造框架、生产级参考后端或额外工具链。

## 设计与实现步骤

1. **确定契约与目标。** 查明计算含义、有效输入、误差与可复现性要求、运行规模、资源限制和实际支持目标。区分已知事实、必要假设与待验证项。
2. **识别主导成本。** 从完整路径检查计算、数据运动、容量、启动与通信、协调、负载分布和关键路径。先说明预期瓶颈与依据，不先选优化技巧。
3. **选择最小必要边界。** 把稳定的计算语义与变化的表示、映射和资源策略适当分开。边界可以由函数、模块、数据结构或库接口承载，不强制某种对象模型。
4. **选择信息的绑定时机。** 明确哪些信息何时可知、稳定多久、重复使用多少次，再在普通参数、批量分派、预处理计划、静态特化或生成代码之间选择。
5. **联合安排数据与工作。** 评估表示、访问、放置、生命周期、工作粒度、依赖、负载均衡及其交互。给出影响正确性和组合的完成与回收契约。
6. **实现并验证假设。** 保持独立正确性参照，用代表负载评价端到端目标，必要时用微基准解释机制。报告代价、覆盖边界与撤回条件；未测量时只陈述性能假设。

这些步骤是推理顺序，不要求每次输出六节报告。已有设计和基准可以直接复用，不重复建设。

## 绑定时机决策必须回答的问题

- 哪些事实已经可知，哪些会随输入、部署或执行阶段变化？
- 提前确定后消除了什么重复工作或不确定性，收益能否摊销？
- 应在编译、计划构建、任务提交还是内部循环之前确定？
- 增加多少代码版本、构建成本、容量、诊断与验证负担？
- 若使用模板元编程，它实际完成何种类型推理或结构生成，普通泛型、运行时计划或有限分派为何不足？

## 评审与交付

优先指出违反计算契约、依赖、访问权限和生命周期的问题，再讨论主导成本、抽象边界与复杂度。每项意见给出位置或设计对象、影响条件、推理依据、最小调整和验证办法。不要将个人风格偏好包装成性能问题。

输出代码或设计时，简述关键选择、舍弃方案的原因、适用范围和验证状态；原则编号仅用于追溯，不机械输出全部检查表。具体命名、文件组织和语法规则服从项目约定，关注语义是否清楚、显著成本是否可发现。

性能结论必须附与目标相称的实验依据。源码机制、编译通过、统一接口、异步提交和局部示例都不构成普遍速度证明。区分已实现、正确性已验证、性能已测与未覆盖配置。

案例的作用是说明原则如何落地、暴露哪些限制，而非规定新工程也要复制它的结构。面对未在案例中出现的算法或语言，仍从计算契约和成本模型推导，不退回类比 API 名字。
