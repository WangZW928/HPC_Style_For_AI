# 绑定时机与模板元编程：从原则到实现

_通用原则 G05、G09 的按需补充；不是所有 HPC 项目都需要静态特化。_

## 先问事实何时可知，再问用什么语法

提前绑定的目标，是在信息稳定后省掉后续重复工作，或建立更强的合法性约束。编译期并非唯一提前点：一次计算计划的构建、一次任务分组、一次内部循环之前的分派，都可能比编译期固化更合适。

| 决策阶段 | 可解决的问题 | 需要支付的代价 |
| --- | --- | --- |
| 编译或静态代码生成 | 已知类型、有限结构、固定操作组合 | 构建时间、版本组合、产物大小与诊断复杂度 |
| 运行期生成/JIT | 运行时才获知但会重复使用的结构 | 首次生成、缓存管理、部署与回退路径 |
| 计划或预处理阶段 | 重复计算中的索引、分解、布局转换和算法选择 | 预处理、计划存储、更新及失效管理 |
| 批量或任务提交阶段 | 将同类工作分组，一次选择实现 | 分类与批处理延迟、调度复杂度 |
| 逐次或逐元素执行 | 信息持续变化、分派代价可接受 | 重复判断、间接访问与优化可见性限制 |

选择时比较整个使用周期，而不是只比较执行主体。概念上，特化路径的总成本包含构建或准备成本、重复执行成本和维护验证成本；使用次数不足时，单次运行较快也未必值得。

以下是说明原则的假设场景，不是已测结论：重复使用相同稀疏结构时，可考虑预处理计划；只有少数稳定的局部运算组合时，可考虑静态特化；用户任意输入的尺寸，通常先保留运行时值。它们都需要根据更新频率、内存预算和真实瓶颈再决定。

## 为什么使用 C++ 模板元编程

模板首先支持泛型代码，让同一逻辑作用于多种类型。狭义的模板元编程进一步在编译期推理类型、检测表达式、生成有限结构或选择实现。二者相关，但“用了模板”不等于正在做元编程，也不等于已经优化。

适当使用它，通常有以下动机：

- **把类型关系变成接口契约。** 对可写性、元素兼容性或操作能力建立约束，尽早排除不成立的调用。类型正确仍不证明单位、误差或物理模型正确。
- **让静态结构指导实现生成。** 小而固定的秩、异构记录或操作列表可以在实例化时形成具体访问与组合，避免执行时反复解释这些结构。
- **只实例化对该类型有效的实现。** 类型相关分支可以静态裁剪，而输入大小、资源状态和用户选项等真正动态的条件继续运行时判断。
- **向优化器暴露具体操作。** 具体 callable 和操作类型提供内联、传播及简化的机会。实际是否发生以及是否更快，仍取决于工具链和工作负载。

这些动机需要回答“普通参数、普通循环或一次性分派为何不足”。如果答案只是避免一次低频间接调用，多层模板或 CRTP 可能增加更多工程成本。

## 哪些机制应分别理解

| 机制 | 主要作用 | 常见误解 |
| --- | --- | --- |
| 类/函数模板 | 复用带具体类型的实现 | 泛型本身就是速度保证 |
| concepts / traits / 受约束重载 | 判断并表达 API 所需能力 | 表达式成立就等于数值和并行语义正确 |
| `if constexpr` | 按编译期条件保留有效实现 | 可以代替所有动态判断 |
| 常量索引展开 | 生成需要常量索引的结构访问 | 被展开的运行时数组运算已经在编译期完成 |
| 普通运行时循环 | 遍历动态规模的同构工作 | 没用元编程就缺少优化机会 |
| 动态接口 / 类型擦除 | 开放扩展、稳定边界与运行期选择 | 在所有位置都比静态机制差 |
| 预处理和平台注解 | 适配编译配置、语言语法和工具链 | 与模板元编程属于同一种机制 |

新工程使用项目支持的标准设施，现有工程优先局部一致。不要为统一语法全库重写约束，也不要把静态展开、强制内联或平台宏当作性能徽章。

## 为特化设定退出条件

列出元素类型、结构、操作、布局、执行目标等变化轴及实际支持组合；不必为理论笛卡尔积全部生成实现。检查 clean/incremental build、产物体积、错误诊断、指令或寄存器压力，以及目标工作负载收益。

若版本规模持续膨胀，可缩小支持集合、共享非模板部分、显式实例化、转为运行时计划，或在外层一次分派后调用少量具体实现。动态控制与静态计算可以共存，边界取决于成本和扩展需求，而非语言阵营。

最小设计记录应说明：提前绑定了什么、为什么在该阶段绑定、预期消除什么成本、引入多少版本、如何验证，以及何时退回更简单的方案。它适用于模板，也适用于 JIT、生成代码和运行时计划。
