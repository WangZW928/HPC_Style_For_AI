# HPC 通用设计原则

_0.2.0；面向不同算法、语言、并行模型和硬件的设计与评审。_

## 适用方式

HPC 设计的对象不是某一种容器或核函数，而是在**数值正确性、时间、容量、能耗和工程复杂度约束下完成计算**。这些约束在稠密线性代数、稀疏求解、粒子方法、图计算、频域算法与数据处理任务中都存在，具体权重却不同。

以下原则按设计问题组织，不要求工程采用某种类型层次、内存布局、语言特性或执行后端。每条原则都需要落实为当前项目的决策；若缺少相应问题，就不增加对应设施。具体库的实现只能说明原则的一种落地方式，不能确定原则的全部适用边界。

## 先确定计算的含义与代价

### G01：先定义允许保持什么、允许改变什么

优化的边界来自计算契约。先明确输入域、输出含义、误差容限、守恒或其他不变量、失败行为，以及可复现性要求。随后才能决定运算顺序、精度、迭代停止条件和并行分解是否可以改变。

等价不只是一种含义：数学上等价、给定容差内等价、统计意义上等价和逐位相同，允许的实现空间不同。例如，归约重排、混合精度、近似算法与不精确求解器，需要分别满足任务接受的契约，而不是统一以“更快但有误差”处理。

独立正确性参考可以是简单实现、解析结果、小规模穷举、可信实现或可检查的不变量。参考也有覆盖范围；与同一份错误逻辑一致，不构成独立验证。不要求所有工程都维护一个生产级 CPU 后端。

### G02：以完整工作负载的主导成本决定优化方向

先识别约束，再选技巧。建立足够用于决策的成本模型：工作量、有效数据流量、工作集、资源利用率、消息与启动次数、同步等待和关键路径。计算受限、带宽受限、延迟受限、容量受限、负载不均衡可能出现在同一程序的不同阶段。

端到端时间由真实执行依赖决定：有重叠的阶段不应直接相加，串行关键阶段也不应被平均吞吐掩盖。一个核更快，若引入昂贵重排、迁移、初始化或等待，整体仍可能变慢。先改善当前主导项，再重新测量，因为瓶颈会移动。

成本模型是解释与筛选工具，不是测量替代品。忽略缓存、NUMA、网络拥塞或任务进展的理想估计，应写清假设；输入规模和稀疏性分布变化后，原有判断需要复核。

## 组织数据与程序的边界

### G03：联合设计表示、访问、放置与生命周期

数据结构的优劣取决于谁以什么顺序访问、在何处访问、需要保留多久，以及谁有权修改和释放。连续数组、分块结构、压缩表示、对象集合或混合布局，都应服务于真实的操作组合，而非预设一种“高性能布局”。

评估总数据运动，包括格式变换、打包、复制、缓存行放大、跨 NUMA 或设备迁移以及持久化。长期保留第二种表示可能节省重复转换，却支付容量和一致性成本；按需重建可能节省容量，却增加计算与延迟。分配复用也要同时计算峰值占用与资源归属。

共享访问应交代有效范围、可写性、别名关系和失效条件。所有权管理与访问描述可以分离，但不要求一定实现为某一类 owner/view。资源自动释放与消费者已完成是不同保证。

### G04：让抽象围绕稳定语义，让变化局限于适当边界

区分“计算是什么”与“如何表示和执行”。数值操作、问题分解、存储表示、工作分配和资源管理通常具有不同变化原因；边界应允许其中一项调整，而不迫使其他项连带重写。

这不等于每个概念都要一个类，也不等于所有算法都需要统一执行框架。函数、模块、数据描述符、库调用或少量约定都可以承载边界。一个只服务单一任务的小程序，直接表达计算往往比通用框架更清楚。

好的抽象既减少重复，也使重要成本可见：调用是否分配、复制、转换、同步或执行集体操作，应有可发现的契约。调用方不必知道所有内部机制，但应知道影响正确性、组合与性能的行为。

## 决定信息与工作如何进入执行

### G05：在信息足够稳定、收益可摊销时提前绑定

类型、结构、算法选择和资源配置，可以在编译、生成代码、计划构建、任务提交或逐元素执行等不同阶段确定。越早绑定，越可能减少后续解释、分支和间接访问；同时也越可能增加构建成本、代码版本、计划存储和适配限制。

决策依据是信息何时可知、保持多久、重复使用多少次，以及晚绑定到底占用多少成本。固定小结构可能适合静态特化；运行输入决定的大规模结构，可能更适合运行时参数、预处理计划或有限分派。稳定不等于必须编译期确定，动态也不等于必须在每个元素上重新判断。

模板元编程只是提前绑定的一种工具。它值得使用的理由是表达类型关系、排除不成立的实现、生成有限结构，或让优化器获得原本缺少的信息，而不是“模板天然更快”。运行时计划、JIT、批量库接口和普通控制逻辑也应参与比较。C++ 的展开、约束和实例化取舍见[绑定策略说明](<binding-strategies.md>)。

### G06：联合选择粒度、局部性与并行层次

任务太细，调度、启动、消息和协调成本可能压倒有效工作；任务太粗，又可能造成资源闲置、负载不均衡或工作集超出容量。粒度需要同时考虑数据复用、依赖结构、硬件并发和输入分布。

分块、批处理、向量化、线程划分、分布式分区和加速器任务，解决的是不同层次的映射问题。它们应协调，而不是各自最大化并行度；嵌套并行还需要明确资源归属，避免线程过量、带宽争用或重复调度。

不规则任务可以按成本分桶、压缩活跃集合、重新编号或动态调度，但整理本身也有代价。某种划分在均匀输入上有效，不代表能覆盖偏斜图结构、变化的粒子密度或长尾任务。

### G07：将并发正确性表达为依赖与完成契约

先确定哪些工作可以独立发生，再选择线程、消息、任务图或队列。每项共享资源都应有清楚的读写权限、先后依赖、完成条件和回收责任。局部完成、远端可见、全局一致和资源可复用，可能是不同事件。

异步执行只有在依赖允许且运行时能够取得进展时才产生重叠。提交之后仍可能存在打包、等待、背压和隐式同步；接口名称和任务数量都不证明重叠已经发生。缓冲复用要等待对应使用完成，跨执行域访问还需要满足可达性和可见性要求。

选择足够保证契约的协调范围，不额外扩大同步，也不为追求异步而删除必要依赖。同步实现常是更易验证的起点；复杂流水只有在端到端收益足够时才值得保留。

### G08：同时衡量局部效率与整体完成时间

单个处理单元的最高吞吐不一定带来最短作业时间。应将工作均衡、数据局部性、通信、资源竞争和关键路径放在一起评估；必要时牺牲部分局部效率，换取更少等待或更短全局尾部。

重新分区、复制数据、迁移任务和冗余计算，都可能改善整体进度，也都可能增加通信、容量或初始化成本。适合长时间重复执行的昂贵重组，对一次性短任务未必值得。动态负载均衡还要计算观测、决策与迁移开销。

分布式程序关注最慢参与方及其原因，单机多阶段程序关注拖住流水的阶段。只报告平均速率或最快工作单元，会遮蔽这些问题。

## 控制专门化与长期演进的代价

### G09：把特化视为有预算、可撤回的投资

特化、融合、展开、代码生成、定制布局和专用核函数，都在用额外复杂度换取某一工作负载上的收益。为每个版本交代受益范围、维护者需要理解的新约束、构建与产物成本，以及增加的验证组合。

版本规模由独立变化轴共同决定。类型、形状、布局、算法和目标平台的组合若持续增长，应考虑缩小特化集合、共享实现、提前一次分派、使用计划，或回到较通用的路径。融合减少中间数据的同时，也可能增加工作集、寄存器占用和耦合，收益并非单向。

保留可理解的参照路径或独立验证办法，明确收益消失后的简化条件。对于冷路径、低频配置和小任务，较高层抽象或动态机制可能是更便宜的工程选择。

### G10：让代码结构承载推理，而不只是承载实现

模块边界围绕职责、数据契约和变化方向组织；公开接口说明输入输出、单位、范围、所有权、完成语义及显著副作用。命名首先区分语义角色与行为，不以某种大小写或文件后缀充当架构原则。

注释重点解释不直观的不变量、算法条件、性能前提和保留特殊实现的理由。局部短名可以用于清晰的数学或索引语境；跨模块对象应能凭名称和接口辨认用途。具体缩进、前缀和大小写沿用项目约定，不通过全库重排证明规范统一。

设计应缩短“理解一个结果从何而来”的路径。必要的低层代码可以集中并充分约束，外围逻辑保持直接；重复代码与过深抽象都需要按实际认知成本取舍。

### G11：把测量与数值验证纳入设计闭环

每次优化都对应可检验的假设，以及区分结果的实验。记录输入特征、硬件与资源分配、编译和依赖配置、计时边界、预热、重复、波动与数值判据。总时间、峰值内存、误差、构建时间等指标按任务目标选择，不以单个吞吐数字代替整体评价。

验证覆盖边界、极端规模、偏斜输入和关键配置；异步和并行实现增加依赖、可见性与竞争方面的检查。微基准用于解释局部机制，代表性端到端负载用于决定是否保留优化，两者目的不同。

区分机制推断、实现完成、正确性通过和性能已测。尚未测量的改动报告预期机制与待验证条件，不将编译通过、修饰符、统一接口或某个示例的成功写成普遍性能结论。

### G12：将可移植性定义为明确的支持契约

说明希望保持的是数值语义、源代码、功能覆盖、部署便利还是性能目标。支持两个平台，并不自动表示两者具有同样的最优实现；单源码也不意味着调优参数通用。

公共层尽量保持问题语义与可检查契约，适配层处理必要差异，并允许对已证实的热点保留局部专门路径。抽象过低会向业务暴露平台细节，抽象过高又可能隐藏关键能力；边界应允许受控调整，而非追求表面上的绝对统一。

声明实际验证的配置、保底路径和未覆盖条件。新增平台或执行模式时，重新评估数值行为、资源放置、粒度、依赖和成本模型；不要只替换调用语法。

## 对 AI 的最低要求

使用这些原则时，先指出当前任务真正需要解决的设计问题，再选择实现机制。不要为凑齐十二条增加层次、类、模板、后端或基准设施。交付中保留关键决策的理由、适用范围、代价和验证状态即可。

一个判断抽象层级的方法是：换成另一种算法、另一门语言或另一个执行系统后，这条原则是否仍提出有用的问题？若只剩某个具体 API 的用法，它应放入实现说明或案例，而不是通用原则正文。
