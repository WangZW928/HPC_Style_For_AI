# 案例如何支持通用原则

_证据附录；与原则正文分开阅读。_

## 原则、机制和效果是三个层次

[通用原则](<../skills/hpc-style-for-ai/references/rules.md>)按设计问题组织。当前有两个限定范围的源码案例：[AMReX Base 解析](<base-study.md>)及其[证据账本](<../evidence/base-evidence.json>)，以及[Kokkos 对照阅读](<kokkos-study.md>)及其[证据账本](<../evidence/kokkos-evidence.json>)。前者使用 E 编号，后者使用 KM（内存与数据）和 KE（执行）编号；它们提供机制与限制，不替代原则正文。

源码可以证明某个版本使用了哪些接口、布局或分派方式，并帮助解释其适用条件；它不证明这些方式适合所有算法，也不证明实际运行更快。通用原则包含工程推理与建议，不是从两个局部案例形式化推出的定理。尤其不能把 `View`、执行空间或某种 policy 的 API 用法改写成所有 HPC 项目都应遵循的结构规范（KM01、KE01、KE02）。

| --- | --- | --- |

## Kokkos 对照补充了哪些边界

本轮固定 Kokkos 5.3.0、提交 `dc826b0fad122b57fee60223e86154aecb8e60f4`，以 Serial/OpenMP 为 host 路径，并阅读部分 CUDA 实现作后端对照。[Kokkos 账本](<../evidence/kokkos-evidence.json>)中的 KM01–KM12 与 KE01–KE12 分别记录文件、行号、逐字引文、限制及验证办法。以下对照集中于本轮有材料补充的八条原则，不为凑齐十二条补造结论。

| 原则 | Kokkos 证据 | 对 AMReX 案例之外的补充与限制 |
| --- | --- | --- |
| G01 计算契约 | KM10；KE05、KE06、KE07 | copy 的同对象、同 span 与部分重叠需要分别处理；归约分组、scan 的非最终遍副作用、索引窄化及总规模都进入输入输出契约。数学等价、容差一致与逐位一致不是同一要求。 |
| G03 数据联合设计 | KM01、KM02、KM03、KM05、KM08、KM09、KM11 | 访问描述可携带共享分配记录，也可不管理资源；span/stride、条件镜像别名、初始化及双侧修改协议共同影响访问与生命周期。由此支持分开推理，而非强制分成独立 owner/view 类型。 |
| G04 抽象边界 | KM06、KM07、KM08、KM09；KE02、KE04 | 同名 copy/mirror 与统一并行入口之下，可能发生逐元素转换、别名返回或不同范围的等待；输出标量或 View 也会改变 fence。抽象应让这些成本与完成条件可发现，而非以名称代替契约。 |
| G05 绑定时机 | KM01；KE01、KE02、KE07、KE08、KE12 | 静态 extents/layout、索引类型、LaunchBounds 与运行时 extent、实例、tile 和 occupancy 值协作；提前绑定是按信息稳定程度分层，不是把全部资源参数固定为模板实参。 |
| G06 粒度与局部性 | KM05；KE08、KE09、KE10、KE11 | stride、tile、team、vector 与 scratch 预算联动；默认 tile 是受限策略，非最优承诺。team/thread/lane 分工及副作用重数必须明确，Serial 的宽度 1 会掩盖某些重复执行风险。 |
| G07 依赖与完成 | KM02、KM03、KM04、KM06、KM07、KM09、KM11、KM12；KE01、KE03、KE04、KE11、KE12 | 引用计数、可达性、dirty 标志、提交和完成是不同事件；无实例 copy、显式实例 fallback、标量结果与 debug 发射可能等待。team/vector barrier 与实例/全局 fence 的完成范围也不同。 |
| G11 验证闭环 | KM05–KM10、KM12；KE03–KE07、KE09–KE12 | 源码核验给出可检验机制，独立 host probes 只覆盖所选配置与断言；CUDA 重复执行、异步完成及数值重排仍需专门测试。账本中的验证办法不等于这些实验已经执行。 |
| G12 可移植性契约 | KM04、KM07、KM12；KE03、KE08、KE09、KE10、KE12 | 可达不等于数据最新或成本相同；统一源码不保证各后端采用相同 vector 宽度、同步范围或最优 tile。新增后端仍需重验资源、依赖与数值行为。 |

### 哪些说法需要收窄

- **owner/view 的类型划分。** “数据管理与访问分离”不等于必须有一对独立类型。 Kokkos 的 managed 访问对象可以共享 tracker，unmanaged 变体则不恢复所有权；镜像接口还可能返回别名。应检查谁保持资源存活、谁可访问及何时允许释放，而非从对象叫 `View` 推断其无所有权（KM01、KM02、KM08、KM09）。
- **默认参数的适用范围。** 默认配置可移植，不等于默认参数普遍最优。 tile 推荐受实例资源和静态 LaunchBounds 共同限制；host 的 `vector_length_max()` 与 effective vector width 也不是同一量。默认值首先提供当前后端的策略与可行范围，具体收益仍由负载决定（KE08、KE09）。
- **async 的完成条件。** 显式实例或 View 结果不等于必然异步，调用返回也不总是完成。 copy 切换执行域的 fallback 会等待；归约/扫描的标量结果可触发实例 fence，CUDA debug bounds 检查可在发射后等待。反过来，没有公共层 fence 也不证明真正发生重叠（KM06、KM07、KM09；KE03、KE04、KE12）。
- **可移植性的验证层次。** 可访问、可同步、可在 CPU 通过，不等于跨后端契约已经成立。可达性 trait 不迁移数据，DualView 的标志/同步有配置条件；Serial 也不暴露 CUDA 多 lane 下的全部副作用重数。可移植性应声明数值语义、实际映射与验证配置，而非只列统一 API（KM04、KM11、KM12；KE06、KE09、KE10、KE11）。

### 本轮实际验证到哪里

上述 KM/KE 条目首先是限定范围的源码审阅，不是全库审计。主线另编译 Serial+OpenMP，并报告原创[host 契约探针](<../examples/kokkos_contracts.cpp>)在 1 线程和 4 线程的 CTest 配置通过：覆盖 layout 转换、host 镜像别名与独立分配、strided copy、scalar/empty reduce，以及 `TeamThreadRange` 配合 scratch、barrier、single 的所选用例（对应 KM05–KM10、KE04、KE09–KE11 的部分机制）。这些是本项目探针结果，不是声称运行了 Kokkos 全部上游测试；源码条目的待验项也不会因此全部变成已验证。

CUDA 本轮只读实现，未编译运行；没有 GPU 正确性、异步重叠或性能结果。host probes 同样不证明归约跨配置逐位一致、scan 非最终遍副作用正确，或缺失依赖在异步后端仍成立（KE03–KE06、KE10、KE12；KM07、KM12）。完整读取范围、未覆盖项与复核入口见[Kokkos 对照阅读](<kokkos-study.md>)；后续若改变版本、后端或构建宏，应重新核对，而不是沿用本轮结果。

## 将原则迁移到其他问题

以下是用于检验抽象层级的假设场景，不是对这些算法或语言工程新增的源码审计或已完成实验；上文已加入 Kokkos 案例，不改变下列迁移练习的假设性质：

- **稠密计算**：先问计算强度、数据复用与库调用边界；是否需要特化取决于稳定结构和调用次数，而不是必须自己写模板核函数。
- **稀疏或图计算**：先问不规则访问、结构复用、任务长尾与预处理摊销；不预设连续组件布局或网格分块。
- **粒子或动态任务**：先问数据重排、活跃集合、分布变化和迁移成本；容量复用与动态调度分别计算收益和代价。
- **频域或重复变换**：先问计划构建、重复次数、重排与通信；“提前绑定”可以发生在运行时准备阶段，而非必须发生在编译期。
- **Python/Fortran/其他语言工程**：先问计算边界、批量接口、复制、部署与验证；原则不要求为获得静态类型机制而更换语言。

若这些场景的回答最终都退化成“实现一个类似原库的对象体系”，说明仍在复制案例，而没有从约束推导设计。
